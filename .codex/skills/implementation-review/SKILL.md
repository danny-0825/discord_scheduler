# Implementation Review

## 目的

実装がIssueとdocsの契約を満たし、意図しない変更や回帰を含まないことを確認する。レビュー結果はPRコメントに投稿できる形式で整理する。

このSkillは `issue-to-pr-workflow` から呼び出されても、実装レビューだけを単独で依頼されても完結する。他のSkillやフェーズ定義を読み込まないと実行できない前提を置かない。

## 入力と成果物

入力は変更差分またはPR、Issue、docs、テスト結果、関連設定とする。Issueやdocsが提供されない場合は、変更の目的と期待動作を確認できる範囲でレビューし、不足を指摘する。成果物は、重大度付きレビュー指摘、修正後の再レビュー結果、テスト結果、残件と未対応理由である。

## レビュー観点

- Issueの完了条件とdocsの仕様を満たしているか
- 実装のスコープがIssueから逸脱していないか
- 正常系、異常系、境界条件、入力検証が適切か
- エラー処理、リソース解放、再試行、タイムアウトが適切か
- 既存機能の回帰、API/データ互換性、移行影響がないか
- 認証、認可、入力値、秘密情報、ログ、個人情報の扱いが安全か
- 性能、並行性、可観測性、運用上の失敗モードに問題がないか
- テストが完了条件とリスクを十分にカバーしているか
- 差分に不要な変更、デバッグコード、生成物、環境依存がないか
- 可読性、責務分離、命名、保守性が妥当か

## 重大度

- 🔴 必須修正: 要件未達、バグ、テスト失敗、重大な回帰・安全性・互換性問題。解消するまでcommitまたはPR完了へ進めない。
- 🟡 推奨修正: 保守性、テスト、性能、可読性の改善。🔴がある場合は同時に修正する。
- 🟢 軽微・参考: 表記、局所的な改善、将来対応、好み。🔴がある場合は可能な限り修正する。

## 実行手順

1. Issue、docs、変更差分、テスト、設定を確認する。
2. 過去の実装レビューまたはPRレビューコメントから指摘ID、レベル、前回の対応状況を確認する。
3. 指摘を重大度、ファイル・行、問題、理由、修正案、確認方法で記録する。
4. PRコメントまたはレビュー記録の先頭に前回指摘の解消状況表を置き、新規指摘があれば新規指摘一覧表を続けて置く。
5. 表の後ろに指摘IDごとの詳細を投稿する。
6. 🔴があれば実装を修正し、テスト、静的解析、差分レビューを再実行する。修正できない場合は、理由と判断者を記録する。
7. 🔴が残っている間はレビューを完了扱いにせず、修正後に全観点を再確認する。
8. 🔴がなくなったら、🟡・🟢の対応状況と未対応理由を記録して完了する。

## レビューコメント形式

```markdown
| ID | レベル | チェック |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 | ✅ / ⛔️ |

| ID | レベル | 概要 |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 / 🟡 / 🟢 | xxxxxx |
```

### {IssueNo}-{指摘No}

**問題**:

<問題の内容>

**理由**:

<修正が必要な理由>

**修正案**:

<具体的な修正案>

**確認方法**:

<修正後の確認方法>

実際のPRコメントでは、外側のコードフェンスを付けず、このMarkdownをそのまま投稿する。

既存の指摘IDは再利用・変更しない。新たな指摘だけ次の指摘番号を採番する。新規指摘がない場合は、新規指摘一覧に「なし」と記載する。
初回レビューで前回指摘がない場合は、解消状況表に「なし」と記載する。

## 停止条件

次の場合は推測でレビューを完了せず、確認事項として報告する。

- 変更の目的や期待動作を確認できない
- 必要なテスト、ビルド、静的解析を実行できない
- 関連コードや実行環境を確認できず、回帰や互換性を判断できない
- 🔴の対応方針を決める権限または情報がない
