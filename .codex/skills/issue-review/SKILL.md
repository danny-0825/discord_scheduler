# Issue Review

## 目的

Issueを実装可能で検証可能な状態にする。レビュー結果はIssueコメントに投稿できる形式で整理する。

このSkillは `issue-to-pr-workflow` から呼び出されても、Issueレビューだけを単独で依頼されても完結する。他のSkillやフェーズ定義を読み込まないと実行できない前提を置かない。

## 入力と成果物

入力はIssue本文、Issueのメタデータ、関連する既存Issue・docs・コード（利用可能な場合）とする。成果物は、重大度付きレビュー指摘、修正後の再レビュー結果、残件と未対応理由である。

## レビュー観点

- 背景、目的、利用者、期待する価値が明確か
- 対象範囲と対象外が明確か
- 完了条件が具体的で、検証可能か
- 正常系、異常系、境界条件が定義されているか
- 既存機能、データ、API、設定、互換性への影響が整理されているか
- 実装方針が要求と矛盾せず、過剰なスコープを含まないか
- テスト方針と検証方法が定義されているか
- セキュリティ、権限、個人情報、障害時の扱いが必要十分か
- 依存関係、前提、未確定事項、リスクが明記されているか
- Assignees、Labels、Milestone、Leadership、Project等が適切か

## 重大度

- 🔴 必須修正: 要件不足、矛盾、検証不能な完了条件、重大なリスク。解消するまでdocs作成へ進めない。
- 🟡 推奨修正: 明確性、保守性、テスト容易性の改善。🔴がある場合は同時に修正する。
- 🟢 軽微・参考: 表記、補足、将来改善、好み。🔴がある場合は可能な限り修正する。

## 実行手順

1. Issue本文とメタデータを読み、観点ごとに確認する。
2. 過去のIssueレビューコメントから指摘ID、レベル、前回の対応状況を確認する。
3. 指摘を重大度、対象、問題、理由、修正案、確認方法で記録する。
4. Issueコメントの先頭に前回指摘の解消状況表を置き、新規指摘があれば新規指摘一覧表を続けて置く。
5. 表の後ろに指摘IDごとの詳細を投稿する。
6. 🔴があれば、Issue本文またはメタデータを修正する。修正できない場合は、理由と判断者を記録する。
7. 🔴が残っている間はレビューを完了扱いにせず、修正後に全観点を再確認する。
8. 🔴がなくなったら、🟡・🟢の対応状況と未対応理由を記録して完了する。

## レビューコメント形式

```markdown
| ID | レベル | チェック |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 | ✅ / ⛔️ |

| ID | レベル | 概要 |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 / 🟡 / 🟢 | xxxxxx |

### {IssueNo}-{指摘No}

問題: <問題の内容>
理由: <修正が必要な理由>
修正案: <具体的な修正案>
確認方法: <修正後の確認方法>
```

既存の指摘IDは再利用・変更しない。新たな指摘だけ次の指摘番号を採番する。新規指摘がない場合は、新規指摘一覧に「なし」と記載する。
初回レビューで前回指摘がない場合は、解消状況表に「なし」と記載する。

## 停止条件

次の場合は推測でレビューを完了せず、確認事項として報告する。

- Issueの目的や完了条件が複数の意味に解釈できる
- 対象範囲、担当者、必要なメタデータが不明である
- 関連する仕様や既存機能を確認できず、重大度を判断できない
- 🔴の対応方針を決める権限または情報がない
