# Docs Review

コメント投稿時の改行保持は [issue-to-pr-workflowのcomment-posting.md](../issue-to-pr-workflow/references/comment-posting.md) に従う。

## 目的

docsを、Issueと実装の共通契約として利用できる状態にする。docsの種類に応じて不要な観点は除外するが、Issueとの矛盾は必ず確認する。

このSkillは `issue-to-pr-workflow` から呼び出されても、docsレビューだけを単独で依頼されても完結する。他のSkillやフェーズ定義を読み込まないと実行できない前提を置かない。

## 入力と成果物

入力はレビュー対象のdocs、関連Issue、Task ID、独立性判定で定めた読み取り・書き込み範囲、既存docs、関連コードまたは仕様（利用可能な場合）とする。Issueが提供されない場合は、docs自身に記載された目的と完了条件を基準にし、不足を指摘する。成果物は、日本語の重大度付きレビュー指摘、修正後の再レビュー結果、残件と未対応理由である。

SubAgentとして実行される場合は、割り当てられたTask IDとdocsだけを対象にし、他タスクのdocsやIssueを変更しない。docs・Issueの修正やコメント投稿は、明示された権限がある場合だけ行う。

## レビュー観点

- docsがどのIssue・Task・SubAgentの成果物か追跡でき、親Issue・依存Issue・関連Issueとの関係が明示されているか
- docsの対象範囲とwrite scopeが他タスクと競合せず、共通ファイルを変更する場合の所有Taskと直列化が定義されているか
- docsの入力・出力・参照元・後続成果物が実行計画の関係（`depends_on`、`related`、`validates`）と一致しているか
- 複数SubAgentが同じdocsや設定を編集する計画になっておらず、担当とレビュー担当が一意か
- Issueの目的、スコープ、完了条件が正しく反映されているか
- 読者、前提知識、利用シナリオが明確か
- 用語、状態、処理フロー、入出力が一貫しているか
- API、データモデル、設定、権限、エラー、境界条件が必要十分か
- 実装者が判断に迷わない粒度で、過剰な実装指示になっていないか
- 例、図、コード、コマンドが現行仕様と一致しているか
- 既存docsとの重複、矛盾、リンク切れがないか
- セキュリティ、互換性、移行、運用、障害時の扱いが抜けていないか
- docsの配置、命名、フォーマット、更新方法がリポジトリ規約に合うか
- Obsidian-first運用の場合、`docs/governance/obsidian-docs.md`を正規ルールとして、Properties（`type`、`status`、`tags`、`related`、`updated`）、内部Wikilink、MOCからの導線、backlink、テンプレート利用が満たされているか
- Obsidianで開いたときにProperties、Wikilink、backlink、表、コードブロックが意図どおり表示され、通常のMarkdownビューアでも内容を読めるか
- context docsの場合、正規docsとの重複・矛盾がなく、registry、出典、取得日・確認日、Task contextのアーカイブ方針があるか
- 完了条件とdocsの各項目を相互に追跡できるか
- 関連docsを広範に探索する場合、`document-search` SkillのBM25結果を入口にし、上位候補の本文と正規情報源を確認しているか

## 重大度

- 🔴 必須修正: Issueとの矛盾、実装不能な説明、重要な仕様・エラー・安全性の欠落。解消するまで実装へ進めない。
- 🟡 推奨修正: 説明不足、例の改善、保守性や探索性の改善。🔴がある場合は同時に修正する。
- 🟢 軽微・参考: 表記、補足、将来改善、好み。🔴がある場合は可能な限り修正する。

## 実行手順

1. 対象docs、Issue、Task ID、実行計画、独立性判定の範囲、関連コードまたは既存docsを確認する。
2. Obsidian-first運用なら、`docs/governance/obsidian-docs.md`、`docs/templates/document-template.md`、対象docsのProperties、MOC導線、backlinkを確認する。
3. 過去のdocsレビューコメントから指摘ID、レベル、前回の対応状況を確認する。
4. 指摘を重大度、対象、問題、理由、修正案、確認方法で記録する。
5. docsまたはIssueコメントの先頭に前回指摘の解消状況表を置き、新規指摘があれば新規指摘一覧表を続けて置く。
6. 表の後ろに指摘IDごとの詳細を投稿する。
7. 🔴があればdocsを修正し、関連するIssueまたは参照元も再確認する。修正できない場合は、理由と判断者を記録する。
8. 🔴が残っている間はレビューを完了扱いにせず、修正後に全観点を再確認する。
9. 🔴がなくなったら、🟡・🟢の対応状況と未対応理由を記録して完了する。

## レビューコメント形式

```markdown
| ID | レベル | チェック |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 | ✅ / ⛔️ |

| ID | レベル | 概要 |
| --- | --- | --- |
| {IssueNo}-{指摘No} | 🔴 / 🟡 / 🟢 | xxxxxx |
```

### {IssueNo}-{指摘No}

**問題**:

<問題の内容>

**理由**:

<修正が必要な理由>

**修正案**:

<具体的な修正案>

**確認方法**:

<修正後の確認方法>

実際のIssueコメントでは、外側のコードフェンスを付けず、このMarkdownをそのまま日本語で投稿する。

既存の指摘IDは再利用・変更しない。新たな指摘だけ次の指摘番号を採番する。新規指摘がない場合は、新規指摘一覧に「なし」と記載する。
初回レビューで前回指摘がない場合は、解消状況表に「なし」と記載する。

## 停止条件

次の場合は推測でレビューを完了せず、確認事項として報告する。

- 実行計画が存在しない、または対象docsとTask/Agentの対応が確認できない
- docsの目的、対象読者、参照元が不明である
- Issueや既存仕様との矛盾を解消できない
- 現行コードや外部仕様を確認できず、正確性を判断できない
- 🔴の対応方針を決める権限または情報がない
